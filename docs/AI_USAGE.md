# AI Usage

이 문서는 AI가 프로젝트 문서를 사용할 때의 토큰 절약 규칙을 정의합니다.

## 기본 원칙

- AI는 모든 문서를 자동으로 읽지 않습니다.
- AI는 `docs/TASK_REQUEST.md`를 먼저 확인합니다.
- 사용자 요청에 직접 관련된 문서만 추가로 확인합니다.
- 긴 문서는 전체를 읽기보다 제목, 키워드, 관련 섹션을 먼저 검색합니다.
- 관련성이 불분명한 문서는 읽기 전에 사용자에게 확인합니다.
- 작업 완료 후 갱신 문서도 최소화합니다.

## 작업 유형별 우선 참조

- 기획/설계 작성·수정: `design/PROJECT_BRIEF.md`
- 구현 계획 작성: `design/IMPLEMENTATION_PLAN.md`, `docs/PLANS.md`
- 코드 구현: `docs/TASK_REQUEST.md`, 관련 코드, 필요 시 `docs/ARCHITECTURE.md`
- 셰이더/렌더링 작업: 관련 셰이더·렌더 코드, 필요 시 `docs/ARCHITECTURE.md`, `docs/SPEC.md`
- 버그 수정: 관련 코드, 필요 시 `docs/VERIFY.md`
- 성능 최적화: 관련 코드, 프로파일링 결과, `docs/SPEC.md`의 성능 예산
- 구조 변경: `docs/ARCHITECTURE.md`
- 사양/규칙 변경 (게임 규칙, 밸런스, 기술 기준): `docs/SPEC.md`
- 검증/테스트: `docs/VERIFY.md`
- 빌드·컴파일·테스트 실행: `docs/BUILD.md`의 해당 엔진 섹션만
- 완료 이력 확인: 커밋 기록
- 과거 결정 확인: `docs/DECISIONS.md`

## 문서 읽기 제한

- `docs/TASK_REQUEST.md`에 참조 문서가 적혀 있으면 그 문서를 우선합니다.
- 참조 문서가 없으면 작업 유형별 우선 참조만 확인합니다.
- 여러 문서를 읽어야 할 것 같으면 먼저 읽을 후보와 이유를 사용자에게 알립니다.
- 완료 이력이 필요하면 별도 로그 문서보다 커밋 기록을 먼저 확인합니다.
- 확정 결정만 필요하면 긴 기획 문서보다 `docs/DECISIONS.md`를 먼저 확인합니다.
- 대용량 에셋, 바이너리, 빌드 산출물, 서드파티 코드는 요청이 없으면 읽지 않습니다.

## 토큰 절약 수칙

### AI가 지킬 것

**읽기**

- 파일을 열기 전에 검색으로 위치를 먼저 찾고, 필요한 함수나 구간만 읽습니다.
- 요청에 파일이나 위치가 없고 탐색 범위가 넓어질 것 같으면, 탐색 전에 대상 범위를 사용자에게 확인합니다.
- 이미 읽은 파일은 변경되지 않았다면 다시 읽지 않습니다.
- 씬·프리팹·레벨 직렬화 파일(예: Unity `.unity`·`.prefab` YAML), 생성 코드, 로그 전체는 필요한 부분만 검색해서 확인합니다.
- 엔진 API를 확인하려고 엔진 소스나 생성 코드를 열지 않습니다. 엔진 버전을 기준으로 판단하고, 불확실하면 사용자에게 확인합니다.

**실행**

- 명령 출력은 필요한 줄만 걸러서 확인합니다. 빌드는 `docs/BUILD.md`를 따릅니다.
- 같은 방법으로 두 번 실패하면 재시도하지 않고 원인과 대안을 보고합니다.
- 서브에이전트나 병렬 작업은 사용자가 요청했거나 탐색 범위가 매우 넓을 때만 사용합니다.

**작성과 응답**

- 파일 전체를 다시 쓰지 않고 필요한 부분만 수정합니다.
- 긴 코드는 채팅에 출력하지 않고 파일에 바로 작성합니다.
- 응답은 바뀐 것, 검증 결과, 갱신한 문서 위주로 짧게 작성합니다. 사용자가 요청할 때만 자세히 설명합니다.
- 큰 기능은 구현 전에 짧은 계획을 먼저 제시해서, 방향이 틀린 구현을 다시 하는 일을 줄입니다.

### 사용자가 지키면 좋은 습관

**세션 관리**

- 작업 단위(마일스톤)가 끝나면 새 세션으로 시작합니다. 진행 상태는 `docs/PLANS.md`, `docs/DECISIONS.md`, 커밋 기록으로 이어집니다.
- 한 세션을 계속 쓸 때는 대화가 길어지면 요약(`/compact` 등)으로 줄입니다.
- 현재 작업과 관계없는 질문은 별도 세션에서 합니다.

**요청 방법**

- 파일 경로와 함수 이름을 지정해서 요청합니다. 예: "`Fire/CombustibleComponent.cpp`의 `SpreadHeat`만 수정"
- 문제를 알릴 때는 에러 메시지, 기대한 동작, 실제 동작을 한 번에 적습니다.
- 단순 작업에는 가벼운 모델이나 낮은 사고 수준을, 설계나 원인 불명 버그에는 상위 모델을 사용합니다.

**붙여넣는 내용**

- 에러는 스크린샷 대신 텍스트로 붙이고, 첫 번째 에러 위주로 전달합니다.
- 로그는 전체가 아니라 관련 부분만 붙입니다.
- 화면을 보여줘야 할 때만 이미지를 쓰고, 필요한 영역만 잘라서 보냅니다.
- 비주얼 스크립트(Unreal 블루프린트 등)는 노드를 복사해서 붙이지 않습니다. 복사된 텍스트는 매우 깁니다. "BeginPlay에서 X를 호출해 Y에 연결"처럼 말로 설명합니다.

**환경**

- `CLAUDE.md`는 매 세션 읽히므로 짧게 유지하고, 자세한 내용은 `docs/` 문서로 분리합니다.
- 사용하지 않는 MCP 서버와 플러그인은 꺼 둡니다. 도구 설명이 매 요청에 포함됩니다.

## 사용자 확인이 필요한 경우

- 작업 범위가 기획인지 구현인지 불명확할 때
- 여러 문서를 동시에 수정해야 할 가능성이 있을 때
- 기존 규칙·사양과 충돌하는 요청일 때
- 새 시스템, 새 폴더, 새 문서, 새 외부 라이브러리가 필요한 때
- 렌더링 파이프라인, 그래픽스 API, 엔진 설정처럼 영향 범위가 큰 변경일 때
- 요청서에 없는 검증, 결정 기록, 구조 갱신이 필요할 때
