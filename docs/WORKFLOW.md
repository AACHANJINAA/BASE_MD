# Workflow

이 문서는 AI와 함께 그래픽스·게임 개발 작업을 진행할 때의 사용자 개입 흐름과 문서 갱신 기준을 정의합니다.

## 핵심 원칙

- AI는 작업 시작 시 모든 문서를 자동으로 읽지 않습니다.
- 작업 요청은 먼저 `docs/TASK_REQUEST.md` 형식으로 정리합니다.
- AI는 `docs/TASK_REQUEST.md`에 적힌 작업 유형, 참조 문서, 수정 허용 범위를 우선 따릅니다.
- 참조 문서가 지정되지 않은 경우에만 `docs/AI_USAGE.md`의 최소 참조 규칙을 따릅니다.
- 추가 문서 확인이 필요하면, AI는 이유를 설명하고 사용자 확인을 받은 뒤 진행합니다.

## 작업 시작 흐름

1. 사용자는 새 작업이 생기면 `docs/TASK_REQUEST.md`를 복사하거나 갱신해 작업 요청서를 작성합니다.
2. AI는 먼저 `docs/TASK_REQUEST.md`만 확인합니다.
3. AI는 작업 유형과 수정 허용 범위를 파악합니다.
4. AI는 필요한 최소 문서만 추가로 확인합니다.
5. 요청서에 없는 문서 수정, 새 폴더 생성, 큰 구조 변경이 필요하면 사용자에게 먼저 확인합니다.
6. 작업이 끝나면 사용자가 허용한 문서만 갱신합니다.

## 사용자 개입 지점

아래 상황에서는 AI가 바로 진행하지 않고 사용자에게 확인합니다.

- 작업 유형이 불명확한 경우
- 참조할 문서가 지정되지 않았고 여러 문서가 관련될 가능성이 큰 경우
- 새 폴더, 새 시스템, 새 문서, 새 모듈, 새 외부 라이브러리가 필요한 경우
- 기존 기획·사양과 구현 요청이 충돌하는 경우
- 게임 규칙, 밸런스, 승패 조건처럼 플레이 기준이 바뀌는 경우
- 좌표계, 색 공간, 렌더링 파이프라인, 그래픽스 API처럼 기술 기준이 바뀌는 경우
- 성능 예산이나 대상 플랫폼에 영향을 주는 경우
- `docs/TASK_REQUEST.md`에 적힌 수정 허용 범위를 넘어서는 경우

## 스프린트 모드

하루 단위 실무 테스트, 게임잼, 데모 마감처럼 시간이 정해진 작업에서 사용합니다. `docs/TASK_REQUEST.md`의 `작업 모드`에 `스프린트`라고 적으면 적용됩니다.

### 확인 없이 진행해도 되는 것

- 수정 허용 범위 안에서 새 파일, 클래스, 컴포넌트, 에셋 폴더 만들기
- `docs/PLANS.md`, `docs/VERIFY.md`, `docs/DECISIONS.md` 갱신
- 작업 단위가 끝날 때마다 커밋하기
- 빌드 오류나 명백한 버그 수정

### 그래도 확인을 받는 것

- `design/PROJECT_BRIEF.md`의 목표·범위와 충돌하는 변경
- 이미 동작하는 핵심 기능을 다시 설계하는 구조 변경
- 새 외부 라이브러리, 플러그인, 엔진 설정 변경
- 남은 시간 안에 끝나지 않을 것 같은 작업 (대안을 함께 제안)

### 진행 원칙

- 핵심 루프가 처음부터 끝까지 동작하는 것을 최우선으로 합니다. 다듬기는 그 다음입니다.
- 완벽한 구조보다 시연 가능한 결과를 우선하되, 타협한 부분은 `docs/DECISIONS.md`에 이유를 한 줄로 남깁니다.
- 막히는 문제는 오래 붙잡지 않고 우회안을 제시합니다.
- 남은 기능은 삭제하지 않고 `docs/PLANS.md`의 보류 작업으로 옮깁니다. (발표 시 확장 계획으로 활용)
- 기능 동결 시각 이후에는 새 기능을 추가하지 않고 안정화와 정리만 합니다.

## 문서별 역할

- `docs/TASK_REQUEST.md`: 사용자가 AI에게 전달하는 작업 요청서입니다.
- `docs/AI_USAGE.md`: AI가 문서를 적게 읽고 필요한 범위만 확인하기 위한 규칙입니다.
- `design/PROJECT_BRIEF.md`: 프로젝트 개요, 목표, 범위, 핵심 기획을 정리합니다.
- `design/IMPLEMENTATION_PLAN.md`: 기획을 실제 구현 순서와 마일스톤으로 나눕니다.
- `docs/PLANS.md`: 현재 작업 상태, 다음 작업, 보류 작업을 관리합니다.
- `docs/ARCHITECTURE.md`: 폴더, 코드 모듈, 렌더링 파이프라인, 에셋, 씬의 책임 범위를 정리합니다.
- `docs/SPEC.md`: 게임 규칙·밸런스, 렌더링 기준, 단위·좌표계, 성능 예산 등 동작 사양을 기록합니다.
- `docs/VERIFY.md`: 구현 후 확인할 검증 항목과 완료 기준을 정리합니다.
- `docs/DECISIONS.md`: 반복해서 확인할 필요가 있는 확정 결정과 하루 작업 마무리 판단을 짧게 기록합니다.

## 작업 완료 후 갱신 기준

- 구현 계획이나 상태가 바뀌면 `docs/PLANS.md`를 갱신합니다.
- 확정된 기획 결정이 생기면 `design/PROJECT_BRIEF.md` 또는 `docs/DECISIONS.md`를 갱신합니다.
- 구현 순서가 바뀌면 `design/IMPLEMENTATION_PLAN.md`를 갱신합니다.
- 구조나 렌더링 파이프라인이 바뀌면 `docs/ARCHITECTURE.md`를 갱신합니다.
- 플레이 규칙이나 기술 기준이 바뀌면 `docs/SPEC.md`를 갱신합니다.
- 검증 방법이나 완료 기준이 바뀌면 `docs/VERIFY.md`를 갱신합니다.
- 완료된 작업 이력은 커밋 기록을 기준으로 확인합니다.
- 하루 작업이 끝났거나 이후 작업에 영향을 주는 판단이 확정되면 `docs/DECISIONS.md`에 결정만 남깁니다.

## 충돌 처리

- 사용자 직접 요청이 가장 우선합니다.
- `docs/TASK_REQUEST.md`와 다른 문서가 충돌하면 작업 전에 사용자에게 확인합니다.
- 구현 결과가 기존 문서와 달라졌다면 갱신 후보 문서를 먼저 제안합니다.
- 확실하지 않은 내용은 추정으로 확정하지 않고 `docs/PLANS.md`에 확인 필요 항목으로 남깁니다.
